# 需求与验收标准

## 1. 学习目标

通过同一个美食推荐任务，理解 Agent 如何接收目标、选择工具、观察结果、继续推理并给出最终答案；随后比较手写循环、图编排和 TypeScript 生态的差异。

## 2. 目标用户

- 第一次接触 Agent 开发的学习者；
- 已有少量 Python 或 TypeScript 基础，希望理解工程化 Agent 的开发者。

## 3. MVP 用户故事

用户输入城市、天气感受、已有食材、口味或时间限制后，Agent 应：

1. 识别缺少的信息，但只在确实影响推荐时追问；
2. 获取天气与可用食材；
3. 检索候选菜谱并说明匹配理由；
4. 给出一道主推荐和最多两道备选；
5. 输出所选菜品的食材、步骤、预计耗时和必要的安全提醒。

## 4. 功能需求

| 编号 | 需求 | 验收方式 |
|---|---|---|
| F-01 | 支持自然语言描述用餐需求 | 固定样例能得到结构清晰的推荐 |
| F-02 | 四个共享工具在三分支语义一致 | 契约测试结果一致 |
| F-03 | 无匹配菜谱时不编造库内记录 | 返回“未找到”并给出可解释建议 |
| F-04 | 工具失败时能说明失败并降级 | 模拟超时、空数据、未知菜名 |
| F-05 | 能观察模型调用与工具调用阶段 | 使用脱敏摘要，不记录密钥和完整载荷 |
| F-06 | 供应商和模型通过配置选择 | 不修改业务逻辑即可切换 |

## 5. 非功能需求

- 默认最多 8 个 Agent 步骤，避免无限循环。
- 每个外部调用必须有超时；重试次数有上限。
- 付费模型回退默认关闭，并在启用时设置单次预算上限。
- 相同评测用例可在三个分支重复执行并对比。
- 本地菜谱、食材和天气 Mock 不产生写操作。
- 日志默认不包含完整 Prompt、完整工具结果和任何凭据。

## 6. 当前非目标

- 不做账号系统、网页前端、真实下单或支付。
- 不把 Mock 天气替换为真实服务。
- 不引入向量数据库、微调、强化学习或多 Agent。
- 不追求营养或医疗建议的专业准确性。
- 不在第一阶段同时实现三个分支。

## 7. MVP 完成定义

- 分支 1 通过共享核心评测集；
- 失败场景不会无限循环、泄漏凭据或静默产生付费调用；
- 输出能引用使用过的天气、食材和菜谱信息；
- README 能让另一位初学者独立完成配置、运行和验证；
- 再以相同口径实现并比较分支 2 和分支 3。
